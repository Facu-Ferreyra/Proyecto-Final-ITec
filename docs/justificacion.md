# Justificación de herramientas

Para cada herramienta del stack: qué es y qué rol cumple en EasyBot, por qué la elegimos (según lo que necesita el proyecto), qué alternativas consideramos y qué resignamos al elegirla.

## Herramientas principales

| Herramienta | Rol | Por qué | Alternativas | Qué resignamos |
|---|---|---|---|---|
| **React 19** | Biblioteca del frontend: arma la interfaz con componentes. | El formulario del asistente no es fijo: se arma con los campos (`config.fields`) de cada plantilla, y cada tipo de campo (texto, lista, ítems, días) es un componente. El mismo componente de chat se usa en el chat público y en la vista previa. Es lo que el equipo vio en el curso. | Vue, Angular, JavaScript sin biblioteca | React solo resuelve la interfaz: rutas y validación se agregan con otras librerías. Suma un paso de compilación que JavaScript puro no necesita. |
| **Vite 8** | Servidor de desarrollo y armado (`build`) del frontend. | Muestra los cambios al instante. Con sus variables de entorno (`VITE_USE_MOCKS`) armamos un modo de prueba con datos simulados, así el frontend avanzó sin esperar al backend. El `build` genera archivos estáticos que sirve Express. | Create React App (ya no se mantiene), Next.js | No genera páginas en el servidor (SSR) como Next.js: el contenido no se indexa en buscadores. No lo necesitamos: el chat de cada bot se comparte por link. |
| **Node.js + Express 5** | Entorno y framework del backend: expone la API REST. | Todo el equipo programa en JavaScript en frontend y backend, y compartimos las reglas de validación con Zod. Express permite encadenar middlewares por ruta (`requireAuth`, `requireRole`, control de dueño, límite de pedidos). La versión 5 manda solos al manejador de errores los errores de las funciones `async`. | NestJS, Fastify, Django | Express no impone estructura: la organización en `modules/` la definimos nosotros. Fastify tiene mejor rendimiento, pero para la cantidad de usuarios de un MVP no hace diferencia. |
| **PostgreSQL (Neon)** | Base de datos principal, alojada en la nube. | Los datos son relacionales: usuario → bots → conversaciones → mensajes y leads. Necesitamos integridad: al borrar un bot se borran sus conversaciones y leads (`onDelete: Cascade`), y no se puede borrar una plantilla que usan bots (`Restrict`). Las columnas `Json` guardan los datos que cambian según la plantilla (`config` del bot, `data` del lead) sin perder las relaciones. Neon tiene plan gratuito y se conecta con una URL. | MongoDB Atlas, MySQL, Supabase | Cambiar el modelo requiere migraciones. El plan gratuito limita el almacenamiento y suspende la base sin uso, así que la primera consulta tarda más. Dependemos de un proveedor externo. |
| **Prisma 6** | ORM: conecta el backend con la base de datos. | `schema.prisma` describe las 6 entidades en un solo lugar y las migraciones quedan versionadas en el repo. Las consultas son parametrizadas, sin SQL armado con texto del usuario (R7). Filtrar por dueño (`where: { ownerId }`) hace simple el aislamiento de datos entre usuarios. | Sequelize, Drizzle, SQL directo con `pg` | Suma un paso (`prisma generate`) y una capa más entre el código y la base. Las consultas muy complejas se controlan menos que con SQL directo. Los campos `Json` no se validan en la base: los valida Zod. |
| **JWT en cookie httpOnly + bcrypt** | Autenticación: sesión del usuario y guardado de contraseñas. | Las contraseñas se guardan con hash (bcrypt), nunca en texto. El token vive en una cookie httpOnly que JavaScript no puede leer (protege de scripts maliciosos), con `sameSite` contra pedidos de otros sitios y vencimiento (`JWT_EXPIRES_IN`). Como frontend y API están en el mismo dominio, la cookie funciona sin configuración extra entre dominios. | Sesiones en el servidor (`express-session`), Auth0, Clerk, token en `localStorage` | Un JWT no se puede anular antes de que venza. Lo compensamos consultando la base en cada pedido: si la cuenta se desactiva, deja de funcionar enseguida (aunque eso suma una consulta por pedido). Hay que configurar bien `secure` y `sameSite`. |
| **Render** | Deploy: un solo servicio web con el backend y el frontend compilado. | Express sirve el `build` de React (`client/dist`), así que toda la app tiene una sola URL con HTTPS: no hay problemas de CORS ni de cookies entre dominios. Tiene plan gratuito y despliega desde GitHub. | Vercel (frontend) + Railway (backend), Netlify | El plan gratuito "duerme" el servicio tras un rato sin uso: el primer pedido tarda unos segundos (lo avisamos en el README). Frontend y backend se despliegan juntos y no se pueden escalar por separado. |

## Otras herramientas

| Herramienta | Rol | Por qué | Alternativas | Qué resignamos |
|---|---|---|---|---|
| **Zod 4** | Validación de datos en frontend y backend. | El backend valida todo pedido con esquemas Zod. En el frontend copiamos las mismas reglas para avisar errores antes de enviar, con mensajes en español (`z.locales.es()`). La validación del frontend es solo para la experiencia de uso: el que decide es el backend. | Joi, Yup, `express-validator` | Las reglas del formulario quedan escritas dos veces (frontend y backend): si cambian en una, hay que actualizar la otra. |
| **React Router 7** | Rutas del frontend. | Separa las páginas públicas (`/`, `/login`, `/chat/:slug`) de las privadas (`/bots`, `/panel`) y de las de admin (`/admin`), con rutas protegidas que llevan al login. | TanStack Router, manejar rutas a mano | Las rutas protegidas solo mejoran la experiencia: la seguridad real está en el backend (401 y 403). El servidor tiene que devolver `index.html` en cualquier ruta para que recargar funcione. |
| **helmet, cors y express-rate-limit** | Seguridad básica del backend. | `helmet` agrega encabezados de seguridad. `cors` solo acepta el dominio del frontend (`CLIENT_URL`). `express-rate-limit` limita los intentos de login y registro, y la cantidad de pedidos a toda la API (incluido el chat público, que no pide login). | Configurar los encabezados y límites a mano | Los límites en memoria se pierden al reiniciar el servidor y no se comparten si hubiera más de una instancia. |

## Servicio de IA en el producto

No aplica: EasyBot no consume un modelo de IA. Los bots responden con flujos y reglas fijas según la plantilla. Lo elegimos así porque un comercio necesita respuestas exactas (precios, horarios, turnos), sin costo por mensaje ni respuestas inventadas. La IA se usó en el proceso de desarrollo: ver [uso-de-ia.md](uso-de-ia.md).
